# ГАРАНТ API — коммерческий, почти идеальный по составу

Единственный найденный источник, который **прямо отдаёт редакционную
историю статьи** в структурированном виде.

## Эндпоинты

```
POST /v2/search                              поиск
GET  /v2/topic/{id}                          документ
GET  /v2/topic/{id}/html                     текст документа в HTML
GET  /v2/topic/{id}/entry/{entry}/html       конкретный блок (статья) в HTML
GET  /v2/redactions/{id}                     список редакций
POST /v2/find-modified                       что изменилось
POST /v2/block-on-control/changed            изменилась ли конкретная статья
```

Есть и официальный MCP-сервер.

## Что даёт `redactions`

Ответ содержит:

- `activity[]` — периоды действия редакции (`from` / `to`);
- `changingDocuments[]` — чем внесено изменение;
- `status` — `rs_Actual`, `rs_Old` и прочие;
- `notSure[]` — **периоды неопределённости**.

Это ложится на доменную модель `NormVersion` почти дословно, а `notSure[]`
совпадает с принципом «не скрывать неопределённость» из инженерных правил
проекта.

Главное преимущество перед ИПС: **периоды действия вместо дат актов**.
То есть ГАРАНТ снимает ровно ту оговорку, из-за которой границы редакций
у ИПС приходится проставлять вручную.

## Лимиты

- 30 запросов в минуту на документ;
- 300 документов в `find-modified`;
- 20 секунд на запрос;
- коды `423` и `429` при превышении.

## Условие доступа

Не бесплатный и не открытый: нужен Bearer-токен, который выдаёт
обслуживающая организация пользователям соответствующего комплекта
ГАРАНТ. Токена у проекта нет, сроки получения неизвестны.

## Нерешённый лицензионный вопрос

Документация описывает технику, но не условия использования. Не выяснено:

- допускает ли лицензия использование API в конкурсной работе;
- можно ли хранить полученные тексты в своей базе;
- что происходит с системой, когда подписка кончается.

Вопрос стоит задавать **в той же заявке**, что и токен: ответ влияет на
то, имеет ли смысл интеграция вообще. После выбора ИПС основным
источником вопрос перестал быть блокирующим.

## Честная оговорка про фикстуры

Клиент в проекте написан по документации, **ни один ответ вживую не
наблюдался**. Поэтому файлы заглушки обязаны объявлять `"assumed": true`:
предположение по документации не должно однажды сойти за записанный ответ
сервера — тот же принцип, что `synthetic: true` у фикстур дел. Данные из
заглушки помечены `live=False`, и пометка доходит до вывода команды.

Разбор ответа собран в одной функции, чтобы правка после первого реального
запроса была точечной.
