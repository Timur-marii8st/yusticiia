## Окружение

Python 3.11 и новее.

```bash
git clone <адрес репозитория> && cd yusticiia
python -m venv .venv
.venv/bin/pip install -e ".[dev]"     # Linux/macOS
.venv\Scripts\pip install -e ".[dev]" # Windows
```

Дополнительные наборы зависимостей: `pg` — драйвер PostgreSQL и pgvector,
`ocr` — распознавание сканов. Полный набор для разработки:
`pip install -e ".[dev,pg,ocr]"`.

Параметры развёртывания читаются из окружения, образец —
[.env.example](.env.example). Секреты в репозиторий не попадают никогда.

## Ежедневный цикл

| Действие | Linux/macOS | Windows |
|---|---|---|
| Запуск приложения | `make dev` | `.venv\Scripts\second-opinion serve` |
| Тесты | `make test` | `.venv\Scripts\pytest` |
| Линтер | `make lint` | `.venv\Scripts\ruff check .` |
| Автоисправление | `make fmt` | `.venv\Scripts\ruff check --fix .` |
| Типы | `make types` | `.venv\Scripts\mypy` |
| Оценка качества | `make eval` | `.venv\Scripts\second-opinion eval` |

Приложение поднимается на `http://127.0.0.1:8000`, по умолчанию офлайн:
языковая модель заменена детерминированным моком, внешние обращения
выключены.

## Что проверяется перед коммитом

```bash
ruff check .                        # линтер
mypy                                # типы
pytest --cov                        # тесты и порог покрытия 80%
second-opinion norms-seal --check   # если менялся корпус норм
python -m evaluation.run            # если менялись извлечение, поиск или правила
```

Шестнадцать тестов работают против настоящего PostgreSQL и **без
переменной окружения молча уходят в пропуск** — прогон выглядит зелёным,
ничего не проверив. Поднять базу:

```bash
docker run -d --name so-test-pg -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=second_opinion_test \
  -p 55432:5432 pgvector/pgvector:pg16

SO_TEST_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:55432/second_opinion_test \
  pytest --cov
```

Тот же набор проверок выполняет непрерывная интеграция на двух версиях
Python — [.github/workflows/ci.yml](.github/workflows/ci.yml).

## Зависимости образа

Образ ставит зависимости из `requirements.lock`: версии закреплены, хэши проверяются
(`pip install --require-hashes`). Файл составлен по зависимостям `pyproject.toml` с
дополнениями `pg` и `ocr` для Python 3.11. После изменения зависимостей:

```bash
pip install pip-tools
pip-compile --extra pg --extra ocr --strip-extras --no-header --no-annotate --output-file=requirements.nohash pyproject.toml
```

затем к каждой строке `имя==версия` добавляются `--hash=sha256:...` для всех файлов
этой версии на PyPI (список даёт `https://pypi.org/pypi/<имя>/<версия>/json`). Тест
`test_lock_pins_every_runtime_dependency` следит, чтобы у каждой прямой зависимости
была закреплённая версия с хэшами.

## Правила, которые не обсуждаются

Система проверяет проект судебного акта. Отличие от обычного веб-приложения
одно, но оно определяет всё: **каждое утверждение раскрывается до
источника**.

```text
вывод -> юридический факт -> цитата из документа -> правило -> редакция нормы -> источник
```

Полный список инвариантов с обоснованием — раздел 5 [docs/TZ.md](docs/TZ.md).
Чаще всего ломают эти:

- **Цитата обязана дословно находиться в документе.** Если текст всё-таки
  нужно изменить (например, обезличить перед передачей внешней модели),
  замена обязана сохранять длину — иначе оффсеты поедут и факты отсеются
  как выдуманные.
- **Норма применяется в редакции на юридически значимую дату**, а не в
  текущей. Свежая редакция не подставляется молча — ни в коде, ни в
  плановой автоматике.
- **Статистика не основание для наказания.** Формулировки «следует»,
  «рекомендуется», «завышен», «занижен» в описательных выводах запрещены
  и проверяются тестом.
- **Машинно полученный текст нормы остаётся черновиком**, пока его не
  сверит юрист; правило движка не добавляется без нормы-основания со
  статусом `verified`.
- Документы не отправляются во внешний контур без явного решения
  оператора.

## Раскладка исходников

```text
src/second_opinion/
  analytics/        описательная статистика по выборке дел
  api/              HTTP: сборка приложения, роутеры по ресурсам, схемы
  audit/            журнал операций (хэши и версии, без текстов)
  auth/             учётные записи, пароли, токены, ограничитель входов
  cli/              консольные команды
  domain/           модели: факты, нормы, отчёт, пользователи
  export/           заключение в .docx
  fact_extraction/  паттерновый и модельный извлекатели
  ingestion/        парсеры TXT, Markdown, DOCX, PDF и OCR-фолбэк
  legal_rag/        поиск по базе норм с обязательным цитированием
  legal_sources/    корпус норм, редакции, опечатывание, сверка с ИПС
  llm/              интерфейс языковой модели и адаптеры
  pipeline/         AnalysisPipeline — фасад; ingestion.py и derivation.py — сотрудники
  prompts/          версионируемые промпты (часть пакета)
  retrieval/        подбор сопоставимых дел
  rule_engine/      детерминированные проверки; rules/ — по предмету
  static/           интерфейс судьи
  storage/          файловые и PostgreSQL-репозитории за протоколом

  reporting.py      изложение дела и проблемные места
  privacy.py        обнаружение и маскирование персональных данных
  fact_values.py    допустимые значения обстоятельств
  config.py         параметры развёртывания из окружения
  metrics.py        счётчики и гистограммы
  prompts.py        загрузка промптов
  logging_utils.py  запись стадий разбора

evaluation/         метрики, датасеты, отчёты
data/fixtures/      нормы и синтетические дела
tests/unit/         быстрые проверки отдельных модулей
tests/integration/  проверки через API и конвейер целиком
```

Раскладка проверяется тестом: описание выше и каталоги на диске обязаны
совпадать.

Соглашения по оформлению кода (слои, классы, тесты) ведутся вне
репозитория: это рабочая инструкция, а не описание системы. Комментарии
`#` в коде не используются, кроме директив инструментов (`noqa`,
`pragma: no cover`, `type: ignore`): пояснения лежат в докстрингах и в
`docs/`.

## Документация

Указатель по всем документам — [docs/README.md](docs/README.md).

Архитектурные решения, которые трудно обратить (хранилище, внешний
провайдер, модель данных, источник норм), фиксируются в
`docs/ADR/ADR-NNN-краткое-имя.md` по схеме «контекст -> решение ->
последствия» до реализации. Принятое решение не переписывается — пересмотр
оформляется новым ADR со ссылкой на прежний.

Правила оформления:

- документ отвечает на один вопрос и говорит, кому он адресован;
- заголовок первого уровня один, дальше по иерархии без пропусков;
- проза переносится по 80 символов — так читается diff; таблицы, схемы,
  команды и ссылки не ломаются переносом;
- у блока кода указан язык (`text` для схем и деревьев каталогов);
- ссылка относительная и обязана открываться;
- утверждение о состоянии системы сопровождается датой или способом
  проверки. «Работает» без даты через месяц становится неправдой.

Первые четыре правила и открываемость ссылок проверяются тестом
`tests/unit/test_repository_layout.py`.

Документ, отставший от кода, хуже отсутствующего: ему верят. Если правка
меняет поведение, документация правится в том же коммите.

## Работа сделана, когда

- код написан и запускался вживую, а не только в тестах;
- есть тесты, и проверено, что они падают на сломанном поведении;
- `ruff`, `mypy`, `pytest` зелёные; при изменении корпуса норм — корпус
  опечатан, при изменении извлечения, поиска или правил — пороги
  `evaluation` не нарушены;
- документация отражает то, что код делает на самом деле;
- обновлён [CHANGELOG.md](CHANGELOG.md), включая то, что пошло не так по
  дороге: запись о собственной ошибке дороже записи об успехе;
- версия пакета (`pyproject.toml` и `src/second_opinion/__init__.py`) равна
  `0.N.0`, где N - номер последней записи CHANGELOG; тест
  `test_package_version_matches_the_latest_changelog_entry` следит за этим.
