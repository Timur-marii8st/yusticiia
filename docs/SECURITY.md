# SECURITY

Модель угроз и текущее состояние защиты. Каждая угроза имеет статус:
**закрыто** (реализовано в коде, есть тест), **частично** (реализовано
базовое, известны ограничения), **принятый риск** (осознанно отложено,
см. ROADMAP).

## Режимы авторизации

| Режим | `/api/*` принимает | Актор в аудит-журнале | Когда применять |
|---|---|---|---|
| `open` | всех | `anonymous` | демонстрация на loopback |
| `shared` | общий секрет или личный токен | `shared-token` или судья | быстрый показ по сети, учётные записи ещё не заведены |
| `accounts` | только личный токен | конкретный судья | боевой режим |

Режим задаётся `SO_AUTH_MODE`. Пустое значение сохраняет прежнее
поведение: задан `SO_AUTH_TOKEN` — `shared`, не задан — `open`.

Почему это важнее, чем кажется: до появления режимов защита включалась
ровно одним способом — заданием общего секрета. Пока его нет, `/api/*`
был открыт **даже там, где заведены учётные записи**. Под общим секретом
все действия попадают в журнал обезличенно (`shared-token`), то есть
восстановить, кто подтвердил обстоятельство или удалил документ,
невозможно — для судебной системы это неприемлемо иначе как на время
демонстрации.

## Фундаментальный принцип

**ТЕКСТ ДОКУМЕНТА — НЕДОВЕРЕННЫЕ ДАННЫЕ.** Всё содержимое загруженного
судебного документа рассматривается как данные, никогда — как инструкции.

## Угрозы и меры

### 1. Prompt injection через судебный документ — закрыто

Сценарий: в тексте документа написано «Ignore previous instructions…» или
«верни факт X».

Меры:

- системная инструкция провайдера явно объявляет документ недоверенными
  данными (`src/second_opinion/llm/openai_compatible.py`, SYSTEM_INSTRUCTION);
- недоверенный текст ограждается маркерами «НАЧАЛО/КОНЕЦ НЕДОВЕРЕННОГО
  ТЕКСТА ДОКУМЕНТА» и не смешивается с инструкциями;
- промпт `prompts/fact_extraction_v1.md` §«Системная рамка» запрещает
  считать инструкции документа;
- инвариант приёма результата: цитата модели обязана дословно присутствовать
  в документе, иначе факт отбрасывается (`fact_extraction/llm_extractor.py`);
  выдуманная injection-ом «цитата» не пройдёт эту проверку;
- LLM-факты получают статус LIKELY до подтверждения человеком;
- тест: инструкция «Ignore previous instructions…» в документе не добавляет
  фактов (`tests/unit/test_llm_extractor.py`).

Остаточный риск: инъекция может повлиять на содержимое цитируемого факта,
если она дословно присутствует в документе; финальный барьер — человек
в контуре (подтверждение каждого факта).

### 2. Отравление базы источников (RAG poisoning) — частично

Сценарий: добавление ложной «нормы» в хранилище → поиск выдаёт её как
источник.

Меры:

- поиск возвращает только фрагменты реально хранящихся редакций
  (`legal_rag/search.py`), генерация ответов из ничего отсутствует;
- каждая редакция несёт SHA-256, `source_document`, `source_url`,
  `retrieved_at`, `verification_status`; целостность цитирования
  контролируется метрикой `citation_integrity` (=1.0) в `make eval`;
- фикстуры несут `verification_status` (`verified` после сверки 03.09.2026;
  синтетика помечена отдельно) и юридически сверяются перед
  демонстрацией (см. docs/DATA_SOURCES.md).

Отстаточный риск: целостность хранилища сейчас = целостность файлов в
`data/fixtures/norms`; контроль доступа к каталогу — ответственность
оператора (см. DEPLOYMENT.md). Подпись источников не реализована.

### 3. Вредоносный PDF/DOCX — частично

Меры:

- белый список расширений; отказ для пустых файлов, файлов свыше лимита
  (`SO_MAX_UPLOAD_BYTES`, по умолчанию 5 МБ), бинарного мусора, PDF без
  текстового слоя (`ingestion/parser.py`; тесты);
- парсеры (pypdf, python-docx) работают в процессе приложения; ошибки
  парсинга перехватываются и превращаются в HTTP 400, а не в падение.

Принятый риск: полный sandbox для парсинга (отдельный процесс/контейнер)
не реализован; используются поддерживаемые библиотеки, версии фиксируются.
Обновления зависимостей — см. п. 8.

### 4. Утечка PII / чувствительных документов — частично

Меры:

- дефолт полностью офлайн: `SO_LLM_PROVIDER=mock`, внешние вызовы
  отсутствуют; включение внешнего контура — только явной конфигурацией
  (docs/PRIVACY.md, DEPLOYMENT.md);
- аудит-журнал не содержит сырых текстов: только идентификаторы, хэши
  SHA-256, версии правил/промптов/модели (`audit/trail.py`);
- логи LLM-провайдера не включают содержимое документа.

Принятый риск: обезличивание входных документов перед анализом не
выполняется автоматически — документы обрабатываются «как есть» локально;
оператор обязан соблюдать режим секретности (PRIVACY.md).

### 5. Утечка API-ключей — закрыто (в рамках репозитория)

- ключи читаются только из окружения (`SO_OPENAI_API_KEY`); хардкод
  запрещён конвенцией проекта и `.gitignore` исключает `.env`;
- без ключа внешний провайдер не инициализируется (ValueError на старте),
  система остаётся на мок-провайдере;
- `.env.example` содержит только пустые значения-заглушки.

### 6. Несанкционированный доступ — частично

По умолчанию MVP слушает `127.0.0.1` и предназначен для локальной работы.
Реализовано **два независимых слоя** авторизации:

- **Loopback-MVP:** `SO_AUTH_TOKEN` (общий секрет, Bearer) — включается
  переменной окружения; все `/api/*` требуют заголовок
  `Authorization: Bearer <токен>`; `/health`, `/metrics`, статика и UI
  открыты. Токен закрывает базу для сетевого развёртывания за обратным
  прокси, но не заменяет персональные учётные записи.
- **JWT (итерация 0.17):** `/auth/login` (email+пароль) →
  access/refresh-токены; роли `judge` / `clerk` / `admin`; CRUD
  пользователей (`/auth/users`) только под `admin`. Хранилище —
  `UserStore`: файловое по умолчанию (`<data>/store/auth`, 0.24),
  PostgreSQL при `SO_STORAGE_BACKEND=postgres` (0.20: ротация refresh с
  blacklist, `SO_PASSWORD_MAX_AGE_DAYS`, аудит `GET /auth/audit`).
- **Сосуществование слоёв (ADR-008, 0.21):** при заданном `SO_AUTH_TOKEN`
  `/api/*` принимает общий секрет **или** валидный JWT access-токен;
  `/auth/login` и `/auth/refresh` открыты всегда.
- **Разделение секретов (0.24):** ключ подписи JWT — `SO_JWT_SECRET`,
  отдельный от `SO_AUTH_TOKEN`. Общий Bearer раздаётся операторам, и
  знание его не должно позволять подписать токен с ролью `admin`.
  Захардкоженного ключа по умолчанию нет; без `SO_JWT_SECRET` берётся
  случайный на время жизни процесса.
- **Первый администратор (0.24):** заводится вне API —
  `second-opinion create-admin`, пароля по умолчанию нет. Снятие роли,
  деактивация и удаление последнего активного администратора
  отклоняются (409).
- **Ограничение частоты входа (0.27):** `SO_LOGIN_RATE_LIMIT` попыток с
  одного клиента за `SO_LOGIN_RATE_WINDOW_SECONDS` (по умолчанию 20 за
  60 с), сверх лимита — `429` с `Retry-After`. Блокировка учётной записи
  (`SO_LOGIN_MAX_ATTEMPTS`) считает неудачи по пользователю и потому не
  сдерживает перебор по списку адресов. За обратным прокси все запросы
  приходят с одного адреса: там лимит должен стоять на прокси —
  `X-Forwarded-For` без списка доверенных прокси не используется, его
  подделывает кто угодно.
- **Проверка привязки при старте (0.24):** запуск на внешнем адресе с
  пустым `SO_AUTH_TOKEN` печатает предупреждение, а при
  `SO_REQUIRE_AUTH=1` отклоняется.

Открытый режим при пустом `SO_AUTH_TOKEN` — осознанное решение ADR-008
для локальной работы, а не упущение: демонстрационный сценарий должен
работать без входа. Ответственность за периметр при сетевом
развёртывании несут пп. 1–3 раздела «Сетевое развертывание»
`DEPLOYMENT.md`.

### 7. Логирование чувствительного текста — закрыто

- аудит: только хэши/идентификаторы/версии (см. п. 4) плюс `actor` —
  кто выполнил действие (`user_id`, `shared-token` или `anonymous`);
- structured logging приложения не пишет тексты документов; в отчётах
  API возвращаются только те данные, которые пользователь сам загрузил.

### 8. Атака через цепочку поставок — закрыто (для известных CVE)

- зависимости минимальны и зафиксированы нижними границами в
  `pyproject.toml`; CI гоняет lint+tests на каждый push;
- **Dependabot** (`.github/dependabot.yml`): pip + github-actions,
  еженедельно, авто-PR на новые версии;
- **pip-audit** в CI в **блокирующем** режиме (`.github/workflows/ci.yml`):
  при известной CVE job завершается ненулевым кодом; локальный прогон
  `pip-audit` — чист; setuptools обновляется в CI перед проверкой.
