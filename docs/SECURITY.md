# SECURITY

Модель угроз и текущее состояние защиты. Каждая угроза имеет статус:
**закрыто** (реализовано в коде, есть тест), **частично** (реализовано
базовое, известны ограничения), **принятый риск** (осознанно отложено,
см. docs/TZ.md, раздел 7).

## Закрыто 19.09.2026

**Выход за каталог хранилища.** `get` и `delete` файлового репозитория
строили путь из идентификатора объекта, и `../secret` читал и удалял файл
рядом с хранилищем. Через HTTP это было недостижимо — маршрут не
совпадает, — но слой не должен рассчитывать на предупредительность
вызывающего: те же методы зовут из CLI и из скриптов. Идентификаторы
проверяются шаблоном, отклонённая попытка попадает в лог.

**Бесконечный рост аудит-журнала.** Журнал ротируется по размеру
(64 МБ по умолчанию): файл закрывается с отметкой времени, рядом
начинается новый. Записи не удаляются и не перезаписываются — это
провенанс, а не отладочный лог; при совпадении отметок времени к имени
добавляется порядковый номер, иначе вторая ротация в ту же секунду
затёрла бы первую.

## Закрыто 06.10.2026 (проверка кода по чеклисту безопасности)

**Чужие дела.** В режиме личных учётных записей любой вошедший судья мог читать,
менять и удалять чужие документы и заключения: проверка владельца стояла только у
удаления заключения и у списка. Теперь владелец проверяется в каждом маршруте
(`api/ownership.py`): чужой объект отвечает `404` с тем же текстом, что и
несуществующий, администратор видит всё, записи без владельца в режиме `accounts`
доступны только администратору. Тест `tests/integration/test_ownership.py` на каждый
маршрут.

**Вход.** Заблокированный аккаунт отвечал `403 «Вход временно заблокирован»`, а
несуществующий `401`: по ответу было видно, что адрес зарегистрирован. Теперь ответ
одинаков, на блокированном пути тоже считается хэш пароля (одинаковое время).
Общий секрет `SO_AUTH_TOKEN` сравнивается за постоянное время.

**Нагрузка.** Частота запуска анализа ограничена на пользователя
(`SO_ANALYZE_RATE_LIMIT`), одновременных анализов не больше `SO_ANALYZE_MAX_CONCURRENCY`,
длина ответа модели ограничена `SO_LLM_MAX_TOKENS`; сверх лимита `429` и `503`.

**Факты модели.** Факт со статусом `LIKELY` не участвует в проверках, пока судья не
подтвердил его (отчёт называет такие факты в проблемных местах). Признаки со значением
`false`, стадия «оконченное» и стадия «покушение» или «приготовление» без слова
стадии в цитате не принимаются; сборщик дела не добавляет обстоятельство при `false`.

**Транспорт и ошибки.** Заголовки `X-Content-Type-Options`, `X-Frame-Options`,
`Referrer-Policy`, строгий `Content-Security-Policy` (без встроенных скриптов и стилей),
`Cache-Control: no-store` для `/api` и `/auth`. Документация API (`/docs`, `/redoc`,
`/openapi.json`) в режимах `shared` и `accounts` скрыта (`SO_API_DOCS=1` возвращает).
Тело запроса ограничено до разбора (`413`), в том числе без `Content-Length`.
Непредвиденная ошибка отдаёт `500` без внутренностей и с идентификатором запроса,
трассировка идёт только в лог. Ошибка проверки схемы ответа модели пишется в лог без
значений (раньше в журнал попадали фрагменты документа).

**Ввод и данные.** Тип файла сверяется с содержимым (сигнатура PDF и DOCX); имена таблиц
в SQL проверяются шаблоном. Приложение работает в контейнере не от root. В PostgreSQL
приложение подключается ролью `so_app` без прав суперпользователя
(`deploy/postgres-init/01-app-role.sh`). В CI добавлено сканирование секретов в истории
(`gitleaks`, значения тестовых ключей в `.gitleaks.toml`), `pip-audit` уже был.

**Модель.** vLLM принуждён к `--load-format safetensors` (код при загрузке весов не
исполняется) и `--no-trust-remote-code`.

## Закрыто 07.10.2026

**Refresh-токен в `HttpOnly` cookie.** Браузерный интерфейс входит с `"cookie": true`: refresh
приходит в cookie `so_refresh` (`HttpOnly`, `SameSite=Strict`, `Path=/auth`, без срока жизни:
до закрытия браузера), в теле ответа его нет, скрипт страницы его не прочитает. Обновление по
cookie требует заголовок `X-SO-CSRF`, который межсайтовый запрос добавить не может без
разрешения сервера (CORS не включён). Ротация и отзыв прежние, повторное использование
отозванного токена отклоняется; выход отзывает токен и удаляет cookie. За прокси с TLS
задайте `SO_COOKIE_SECURE=1`. Клиентам без браузера по-прежнему доступен refresh в теле.
Интерфейс стал обновлять access сам и восстанавливать вход в новой вкладке.

## Принятые риски и открытые пункты

- **Access-токен в `sessionStorage`.** Его читает любой скрипт страницы, живёт он 30 минут.
  Refresh-токен вынесен в `HttpOnly` cookie (см. выше), поэтому украденный access не
  продлевается. Смягчение остального: строгий CSP, данные не вставляются через
  `innerHTML`, сторонних скриптов нет.
- **Режим `open`** остаётся по умолчанию для демонстрации на loopback; запуск на
  внешнем адресе без авторизации даёт предупреждение, отказ включается `SO_REQUIRE_AUTH=1`.
- **Второй фактор.** Входа по коду из приложения нет: вход по паролю с блокировкой и ограничением
  частоты. Для сетевого развёртывания это добавляется на периметре (VPN, прокси с TLS и вторым фактором).
- **Пароли.** Пароль выдаёт и меняет оператор сервера, поэтому знает его; пользователь сам
  свой пароль сменить не может (формы и метода API нет). Сброса по ссылке нет: он требует
  почтового канала, которого в закрытом контуре нет.
- **Документы в открытом виде.** Тексты хранятся в `data/store` или в БД без шифрования на
  уровне приложения. Порядок резервного копирования (шифрование копии до выноса с
  сервера, проверка восстановления раз в квартал, срок хранения и удаление) описан в
  `docs/PRIVACY.md`, раздел «Резервные копии»; исполняет и проверяет его оператор.
- **Кэш префиксов vLLM** включён по умолчанию (`docs/DEPLOYMENT_VLLM.md`).

## Пароли

| Что | Как устроено |
|---|---|
| Хранение | bcrypt с отдельной солью на каждый хэш; пароль длиннее 72 байт отклоняется, а не усекается |
| Первый администратор | `second-opinion create-admin`: пароль не короче 12 символов, из `--password`, из `SO_ADMIN_PASSWORD` или вводится дважды в терминале; пароля по умолчанию нет; команда работает, только пока в системе нет активного администратора |
| Остальные записи | только оператор командой `second-opinion create-user` (пароль вводится дважды, `--password` или `SO_NEW_PASSWORD`): от 8 до 72 символов (`SO_PASSWORD_MIN_LENGTH`, по умолчанию 8), а администратору не короче 12 на любом пути; роль, имя и блокировку меняет `update-user`, удаляет `delete-user`, список показывает `list-users`; через HTTP-API и интерфейс записи не создаются и не меняются |
| Смена пароля | только оператор (`reset-password`); новый пароль не должен повторять один из последних пяти (`SO_PASSWORD_HISTORY_DEPTH`); на платформе пароль сменить нельзя |
| Срок действия | `SO_PASSWORD_MAX_AGE_DAYS`, по умолчанию 0 (не ограничен); по истечении вход отвечает 403, пока оператор не задаст новый пароль (`reset-password`) |
| Перебор | блокировка записи после `SO_LOGIN_MAX_ATTEMPTS` неудач (по умолчанию 5) на `SO_LOGIN_LOCKOUT_MINUTES` (15), ограничение частоты входа с клиента, одинаковый ответ для неверного пароля, неизвестного адреса и блокировки |
| Забытый пароль | оператор сервера командой `second-opinion reset-password --email ...` (в журнал операций пишется факт сброса, без пароля) |
| Где хранятся записи | файлы `<data>/store/auth` либо PostgreSQL (`SO_STORAGE_BACKEND=postgres`): таблица `users` рядом с документами и отчётами, уникальный адрес на уровне базы, читаемое представление `user_accounts` (адрес, роль, состояние) |

Сброс снимает блокировку, но выданные ранее токены действуют до истечения (access 30 минут,
refresh 7 дней); чтобы отозвать их сразу, смените `SO_JWT_SECRET`.

## План на случай инцидента

1. **Остановить доступ:** `docker compose stop app` (или остановить процесс); файлы
   `data/store` и `audit.jsonl` не удалять, они нужны для разбора.
2. **Отозвать токены:** сменить `SO_JWT_SECRET` и перезапустить сервис, все выданные
   токены станут недействительными; сменить `SO_AUTH_TOKEN`, если им пользовались.
3. **Закрыть учётные записи:** заблокировать затронутые (`second-opinion update-user --active no`),
   проверить вход по журналу `GET /auth/audit`.
4. **Сменить ключи модели:** новый `SO_OPENAI_API_KEY` (один на приложение и vLLM),
   `docker compose --profile vllm up -d --force-recreate`; ключи БД (`SO_DB_APP_PASSWORD`)
   сменить в БД и в окружении.
5. **Разобрать:** по `audit.jsonl` и запросам с `request_id` из ответов; счётчики
   `second_opinion_http_401_total`, `..._403_`, `..._429_`, `..._5xx_` в `/metrics`
   (`SO_METRICS_ENABLED=1`) показывают перебор и перегрузку, их всплеск повод для оповещения.
6. **Сообщить** по порядку из раздела «Порядок сообщения об уязвимостях» ниже.

## Режимы авторизации

| Режим | `/api/*` принимает | Актор в аудит-журнале | Когда применять |
|---|---|---|---|
| `open` | всех | `anonymous` | демонстрация на loopback |
| `shared` | общий секрет или личный токен | `shared-token` или судья | быстрый показ по сети, учётные записи ещё не заведены |
| `accounts` | только личный токен | конкретный судья | боевой режим |

Режим задаётся `SO_AUTH_MODE`. Пустое значение сохраняет прежнее
поведение: задан `SO_AUTH_TOKEN` — `shared`, не задан — `open`.

Почему это важнее, чем кажется: до появления режимов защита включалась
ровно одним способом — заданием общего секрета. Пока его нет, `/api/*`
был открыт **даже там, где заведены учётные записи**. Под общим секретом
все действия попадают в журнал обезличенно (`shared-token`), то есть
восстановить, кто подтвердил обстоятельство или удалил документ,
невозможно — для судебной системы это неприемлемо иначе как на время
демонстрации.

## Фундаментальный принцип

**ТЕКСТ ДОКУМЕНТА — НЕДОВЕРЕННЫЕ ДАННЫЕ.** Всё содержимое загруженного
судебного документа рассматривается как данные, никогда — как инструкции.

## Угрозы и меры

### 1. Prompt injection через судебный документ — закрыто

Сценарий: в тексте документа написано «Ignore previous instructions…» или
«верни факт X».

Меры:

- системная инструкция провайдера явно объявляет документ недоверенными
  данными (`src/second_opinion/llm/openai_compatible.py`, SYSTEM_INSTRUCTION);
- недоверенный текст ограждается маркерами «НАЧАЛО/КОНЕЦ НЕДОВЕРЕННОГО
  ТЕКСТА ДОКУМЕНТА» и не смешивается с инструкциями;
- промпт `prompts/fact_extraction_v2.md` §«Системная рамка» запрещает
  считать инструкции документа;
- инвариант приёма результата: цитата модели обязана дословно присутствовать
  в документе, иначе факт отбрасывается (`fact_extraction/llm_extractor.py`);
  выдуманная injection-ом «цитата» не пройдёт эту проверку;
- LLM-факты получают статус LIKELY и не участвуют в проверках до подтверждения человеком;
- тест: инструкция «Ignore previous instructions…» в документе не добавляет
  фактов (`tests/unit/test_llm_extractor.py`).

Остаточный риск: инъекция может повлиять на содержимое цитируемого факта,
если она дословно присутствует в документе; финальный барьер — человек
в контуре (подтверждение каждого факта).

### 2. Отравление базы источников (RAG poisoning) — частично

Сценарий: добавление ложной «нормы» в хранилище -> поиск выдаёт её как
источник.

Меры:

- поиск возвращает только фрагменты реально хранящихся редакций
  (`legal_rag/search.py`), генерация ответов из ничего отсутствует;
- каждая редакция несёт SHA-256, `source_document`, `source_url`,
  `retrieved_at`, `verification_status`; целостность цитирования
  контролируется метрикой `citation_integrity` (=1.0) в `make eval`;
- фикстуры несут `verification_status` (`verified` после сверки 03.09.2026;
  синтетика помечена отдельно) и юридически сверяются перед демонстрацией
  (см. [DATA_SOURCES.md](DATA_SOURCES.md#покрытие-редакционной-истории-и-сверка)).

Отстаточный риск: целостность хранилища сейчас = целостность файлов в
`data/fixtures/norms`; контроль доступа к каталогу — ответственность
оператора (см. [README.md](../README.md#сетевое-развёртывание-не-loopback)).
Подпись источников не реализована.

### 3. Вредоносный PDF/DOCX — частично

Меры:

- белый список расширений; отказ для пустых файлов, файлов свыше лимита
  (`SO_MAX_UPLOAD_BYTES`, по умолчанию 5 МБ), бинарного мусора, PDF без
  текстового слоя (`ingestion/parser.py`; тесты);
- парсеры (pypdf, python-docx) работают в процессе приложения; ошибки
  парсинга перехватываются и превращаются в HTTP 400, а не в падение.

Принятый риск: полный sandbox для парсинга (отдельный процесс/контейнер)
не реализован; используются поддерживаемые библиотеки, версии фиксируются.
Обновления зависимостей — см. п. 8.

### 4. Утечка PII / чувствительных документов — частично

Меры:

- дефолт полностью офлайн: `SO_LLM_PROVIDER=mock`, внешние вызовы
  отсутствуют; включение внешнего контура — только явной конфигурацией
  (см. [docs/PRIVACY.md](PRIVACY.md), переменные окружения в
  [README.md](../README.md#переменные-окружения));
- аудит-журнал не содержит сырых текстов: только идентификаторы, хэши
  SHA-256, версии правил/промптов/модели (`audit/trail.py`);
- логи LLM-провайдера не включают содержимое документа.

Принятый риск: обезличивание входных документов перед анализом не
выполняется автоматически — документы обрабатываются «как есть» локально;
оператор обязан соблюдать режим секретности (PRIVACY.md).

### 5. Утечка API-ключей — закрыто (в рамках репозитория)

- ключи читаются только из окружения (`SO_OPENAI_API_KEY`); хардкод
  запрещён конвенцией проекта и `.gitignore` исключает `.env`;
- без ключа внешний провайдер не инициализируется (ValueError на старте),
  система остаётся на мок-провайдере;
- `.env.example` содержит только пустые значения-заглушки.

### 6. Несанкционированный доступ — частично

По умолчанию MVP слушает `127.0.0.1` и предназначен для локальной работы.
Реализовано **два независимых слоя** авторизации:

- **Loopback-MVP:** `SO_AUTH_TOKEN` (общий секрет, Bearer) — включается
  переменной окружения; все `/api/*` требуют заголовок
  `Authorization: Bearer <токен>`; `/health`, `/metrics`, статика и UI
  открыты. Токен закрывает базу для сетевого развёртывания за обратным
  прокси, но не заменяет персональные учётные записи.
- **JWT (итерация 0.17):** `/auth/login` (email+пароль) ->
  access/refresh-токены; роли `judge` / `clerk` / `admin`; список записей
  (`GET /auth/users`) и журнал входов только под `admin`, управление записями
  только командами оператора. Хранилище —
  `UserStore`: файловое по умолчанию (`<data>/store/auth`, 0.24),
  PostgreSQL при `SO_STORAGE_BACKEND=postgres` (0.20: ротация refresh с
  blacklist, `SO_PASSWORD_MAX_AGE_DAYS`, аудит `GET /auth/audit`).
- **Сосуществование слоёв (0.21):** при заданном `SO_AUTH_TOKEN`
  `/api/*` принимает общий секрет **или** валидный JWT access-токен;
  `/auth/login` и `/auth/refresh` открыты всегда.
- **Разделение секретов (0.24):** ключ подписи JWT — `SO_JWT_SECRET`,
  отдельный от `SO_AUTH_TOKEN`. Общий Bearer раздаётся операторам, и
  знание его не должно позволять подписать токен с ролью `admin`.
  Захардкоженного ключа по умолчанию нет; без `SO_JWT_SECRET` берётся
  случайный на время жизни процесса.
- **Первый администратор (0.24):** заводится вне API —
  `second-opinion create-admin`, пароля по умолчанию нет. Снятие роли,
  деактивация и удаление последнего активного администратора
  отклоняются (409).
- **Ограничение частоты входа (0.27):** `SO_LOGIN_RATE_LIMIT` попыток с
  одного клиента за `SO_LOGIN_RATE_WINDOW_SECONDS` (по умолчанию 20 за
  60 с), сверх лимита — `429` с `Retry-After`. Блокировка учётной записи
  (`SO_LOGIN_MAX_ATTEMPTS`) считает неудачи по пользователю и потому не
  сдерживает перебор по списку адресов. За обратным прокси все запросы
  приходят с одного адреса: там лимит должен стоять на прокси —
  `X-Forwarded-For` без списка доверенных прокси не используется, его
  подделывает кто угодно.
- **Проверка привязки при старте (0.24):** запуск на внешнем адресе с
  пустым `SO_AUTH_TOKEN` печатает предупреждение, а при
  `SO_REQUIRE_AUTH=1` отклоняется.

Открытый режим при пустом `SO_AUTH_TOKEN` — осознанное решение для
локальной работы, а не упущение: демонстрационный сценарий должен
работать без входа. Ответственность за периметр при сетевом
развёртывании несут пп. 1–3 раздела
[«Сетевое развёртывание»](../README.md#сетевое-развёртывание-не-loopback)
в README.

### 7. Логирование чувствительного текста — закрыто

- аудит: только хэши/идентификаторы/версии (см. п. 4) плюс `actor` —
  кто выполнил действие (`user_id`, `shared-token` или `anonymous`);
- structured logging приложения не пишет тексты документов; в отчётах
  API возвращаются только те данные, которые пользователь сам загрузил.

### 8. Атака через цепочку поставок — закрыто (для известных CVE)

- зависимости минимальны и зафиксированы нижними границами в
  `pyproject.toml`; CI гоняет lint+tests на каждый push;
- **Dependabot** (`.github/dependabot.yml`): pip + github-actions,
  еженедельно, авто-PR на новые версии;
- **pip-audit** в CI в **блокирующем** режиме (`.github/workflows/ci.yml`):
  при известной CVE job завершается ненулевым кодом; локальный прогон
  `pip-audit` — чист; setuptools обновляется в CI перед проверкой.

### 9. Утечка внутренних заметок через `/docs`/`/openapi.json` — закрыто

FastAPI по умолчанию копирует docstring обработчика и Pydantic-модели в
поле `description` схемы, а `/docs`/`/openapi.json` открыты без
авторизации (см. п. 6, `/health`-класс путей). Докстрины в этом
репозитории объясняют внутренние решения — их видел только тот, кто
читает исходники; анонимный посетитель `/docs` видел бы то же самое.

- `_strip_docstrings_from_openapi` (`api/app.py`) вычищает `description`
  из сгенерированной схемы целиком, оставляя форму ответа (пути,
  параметры, модели, `summary`) без изменений — `/openapi.json`
  по-прежнему годится для генерации клиента;
- то же правило действует на статические файлы интерфейса
  (`static/*.js`, `*.css`, `*.html`): в них нет объяснений, доступных
  через «просмотр кода страницы» в браузере;
- проверяется тестом (`test_docstrings_do_not_reach_the_public_schema`).
