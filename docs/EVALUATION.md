# EVALUATION

Оценка качества — часть продукта, а не вспомогательная задача. Система не
считается работающей, если её качество не измеряется.

## Как запустить

```bash
# вариант 1
make eval            # Linux/macOS
# вариант 2 (Windows)
.venv\Scripts\second-opinion eval
# вариант 3
python -m evaluation.run
```

Команда печатает отчёт в консоль, сохраняет его в
`evaluation/reports/eval_<UTC-время>.json` и возвращает ненулевой код выхода,
если нарушен хотя бы один порог приёмки (удобно для CI).

## Структура

```text
evaluation/
    datasets/     # оценочные наборы (входы оценки)
        golden_v1.json      # извлечение фактов: документы + ожидаемые типы фактов
        retrieval_v1.json   # запросы к базе источников + релевантные нормы;
                            # временные кейсы выбора редакции на дату
    metrics/      # чистые функции метрик
        extraction.py       # P/R/F1, evidence correctness, unsupported_claim_rate
        retrieval.py        # Recall@K, MRR, nDCG@K
        temporal.py         # точность выбора редакции на дату
    reports/      # JSON-отчёты запусков (не редактируются вручную)
    run.py        # оркестрация: набор -> метрики -> отчёт -> пороги
```

## Раздел 1. Извлечение фактов (`extraction`)

Датасет: `golden_v1.json` — образцы документов с ожидаемым множеством типов
фактов (разметка вручную), включая **негативный контроль**
(`sample-negative-appeal`: процессуальный документ без обстоятельств дела;
корректное извлечение — пустое множество).

| Метрика | Что измеряет | Порог |
|---|---|---|
| `macro_f1` | P/R/F1 по множеству типов фактов на образец, усреднение макро | ≥ 0.8 |
| `evidence_correctness` | доля доказательств, чья цитата действительно присутствует в тексте по указанным оффсетам | контролируется; цель 1.0 |
| `unsupported_claim_rate_max` | доля VERIFIED-фактов без evidence по образцам | = 0 |
| `per_type` | P/R/F1 и support по каждому типу факта, агрегированно по корпусу | отчётная |

Ключевой принцип: **факт без доказательства не считается подтверждённым**,
поэтому `unsupported_claim_rate` имеет жёсткий порог 0.

## Раздел 2. Поиск по базе источников (`retrieval`)

Датасет: `retrieval_v1.json`, 28 запросов: 18 к нормам УК и УПК РФ и пунктам Пленума,
10 (q19–q28) к пунктам постановления Пленума № 58 и позициям Обзора ВС РФ от 18.12.2024.
Релевантность определена по **содержимому фикстурного корпуса** (`data/fixtures/norms`)
разработчиком — это оценка качества поиска, а не юридическая экспертиза формулировок
норм; разметку q19–q28 стоит проверить юристу.

Раздел выполняется **дважды** — в лексическом и гибридном режимах;
пороги применяются к обоим: реранкинг не должен деградировать качество ниже
приёмки.

| Метрика | Определение | Порог (среднее) |
|---|---|---|
| `recall_at_5_mean` | доля релевантных норм в первых 5 позициях | ≥ 0.8 |
| `mrr_mean` | среднее 1/ранг первой релевантной нормы | отчётный |
| `ndcg_at_10_mean` | nDCG@10 с бинарной релевантностью | отчётный |

Специальные кейсы:

- **Честный пустой ответ** (`expect_empty: true`): запрос, которому не может
  соответствовать ни одна норма корпуса («шпионаж…» — составы вне корпуса).
  Успех = пустой список результатов, а не выдуманный ответ.
- **Целостность цитирования** (`citation_integrity`, порог 1.0): каждый
  возвращённый фрагмент обязан дословно совпадать с текстом реально
  хранящейся редакции, на которую ссылается ответ.

  Контрольная сумма здесь намеренно не проверяется. Валидатор
  `NormVersion` требует `sha256 == sha256(text)`, поэтому редакция с
  несходящейся суммой не создаётся вовсе — сравнение над загруженной
  моделью было тавтологией и не могло упасть ни при какой правке
  фикстуры. Целостность файлов корпуса проверяется до загрузки:
  `second-opinion norms-seal --check` (в CI, блокирующе); `eval`
  выполняет ту же сверку и завершается ненулевым кодом при расхождении.
  Инвариант «результат поиска существует только если есть источник».

## Раздел 3. Временна́я корректность (`temporal`)

Кейсы в `retrieval_v1.json` -> `temporal_cases`: пара «норма + дата» и
ожидаемая версия редакции. Проверяется инвариант временно́й корректности:
`get_norm(norm_id, applicable_at)` возвращает именно ту редакцию, которая
действовала на дату, включая граничные даты интервалов.

| Метрика | Порог |
|---|---|
| `accuracy` | = 1.0 |

## Регрессия правил (Rule Engine)

Правило-движок покрывается детерминированными регрессионными тестами
(`tests/unit/test_rule_engine.py`; черновые правила — `tests/unit/test_draft_rules.py`): каждое правило
проверяется на известных входах со 100% воспроизводимостью, включая
граничные значения. Правило без тестов не добавляется (инвариант И-10 в
[TZ.md](TZ.md)).

## Производительность

`scripts/load_check.py` загружает документ один раз и запускает анализы
параллельно через HTTP API; печатает пропускную способность, медиану, 95-й
процентиль и максимум задержки. Ограничение частоты анализа на время замера
снимается (`SO_ANALYZE_RATE_LIMIT=0`). Замер на рабочей станции разработки
(Apple M4, файловое хранилище, без модели, корпус 115 норм в 221 редакции):

| Документ | Запросов / потоков | Анализов в секунду | Медиана | 95% | Максимум |
|---|---|---|---|---|---|
| образец, 1,7 тыс. символов | 200 / 8 | 434 | 18 мс | 24 мс | 28 мс |
| реальный приговор, 55 тыс. символов | 100 / 4 | 55 | 72 мс | 107 мс | 126 мс |

## Проба языковой модели

Если подключена модель (`SO_LLM_PROVIDER=openai_compatible`), `python -m
evaluation.llm_extraction_probe` сравнивает на том же золотом наборе извлечение одними
паттернами и паттернами вместе с моделью (тот же класс `LLMFactExtractor`, что работает
в приложении) и печатает macro-F1 обоих вариантов, число принятых фактов модели и время
ответа; отчёт сохраняется в `evaluation/reports/`. Результаты замеров и их разбор — в
[CONCEPT.md](CONCEPT.md).

## Расширение наборов

1. Добавьте образец/запрос в соответствующий датасет.
2. Разметка должна быть проверяемой: ожидаемые типы фактов — из текста
   документа; релевантные нормы — из реально хранящихся.
3. Запустите `make eval`; отчёт покажет изменение метрик.
4. Если качество упало ниже порогов — CI/команда вернёт ошибку.

## Ограничения текущих наборов

- Наборы маленькие и синтетические: они проверяют регрессию качества, а не
  дают статистически значимую оценку на реальной популяции документов.
- Реальные судебные документы и официальные тексты норм подключаются только
  после юридической сверки (см. docs/DATA_SOURCES.md) и с учётом требований
  docs/PRIVACY.md.
