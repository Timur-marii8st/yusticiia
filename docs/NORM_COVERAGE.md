# Редакционное покрытие норм

Отчёт: `second-opinion norms-coverage` (с `--strict` — ненулевой код выхода).

## Зачем

Система обещает «норму в редакции, действовавшей на юридически значимую
дату». Обещание держится ровно настолько, насколько полна редакционная
история в `data/fixtures/norms/`.

Из данных не видно разницы между двумя разными утверждениями:

- «статья с 1996 года действительно не менялась» — проверенный факт;
- «мы внесли один текст и считаем, что он действовал всегда» — допущение.

Хранятся они одинаково: одна редакция с `effective_from: 1997-01-01` (до 07.10.2026 стояло
`1996-07-01`: УК РФ введён в действие с 1 января 1997 года) и
пустым `effective_to`. Разница принципиальная: во втором случае на дату
из прошлого система вернёт **не ту** редакцию, причём уверенно и со
статусом `verified` — то есть ровно тот отказ, который продукт обещает
предотвращать. Пробел в покрытии безопаснее: он даёт честную ошибку
`NoApplicableVersionError`.

## Как читать отчёт

Норма попадает в список на сверку, если выполнено одно из условий:

- **разрыв** между редакциями — на дату внутри дыры норма не найдётся;
- **одна открытая редакция дольше 10 лет** у нормы,
  которую читает движок правил, — история изменений не зафиксирована.

Значимой для правил считается норма, у которой есть структурные пределы
санкции либо на которую правило ссылается по `norm_id`
(`rule_engine.rules.REFERENCED_NORM_IDS`; расхождение со ссылками в коде
ловит `tests/unit/test_norm_coverage.py`).

## Чем это делать

Две команды, ни одна не требует внешнего API. То же самое доступно из
браузера: у каждой нормы на панели «Состояние нормативного корпуса» есть
раскрывающийся блок «Свериться с источником» с обеими формами — без
терминала и без имён параметров CLI. Доступ — только роли `admin`
(`docs/API.md`).

**Статья действительно не менялась** — зафиксировать сверку:

```bash
second-opinion norms-confirm-history \
  --norm-id uk-rf:art-66 --checked-through 2026-09-11 --source КонсультантПлюс \
  --source-document 102041891
```

Норма уходит из списка на сверку: единственная редакция перестаёт быть
допущением и становится подтверждённым фактом. Источник обязателен —
утверждение без него ничем не лучше допущения.

`--source-document` — идентификатор документа в ИПС (`nd`; у УК РФ это
102041891). Команда спросит у источника номер текущей редакции и запишет
его в действующую редакцию нормы как **точку отсчёта**
(`pravo:102041891:365`). С этого момента изменение закона обнаруживается
одной командой `second-opinion norms-check-updates`; без отметки она о
норме сказать ничего не может — сравнивать не с чем.

Отметка ставится, только если сверка её покрывает: если дата в
`--checked-through` раньше, чем подписан изменяющий акт последней
редакции, команда откажет. Иначе отметка выглядела бы проверенным
фактом, оставаясь допущением — юрист смотрел текст до этой поправки.

**Статья менялась** — добавить редакцию:

```bash
second-opinion norms-add-version \
  --norm-id uk-rf:art-228-part-1 --text-file ред-2004.txt --effective-from 2004-01-01
```

Интервал предыдущей редакции закрывается автоматически днём раньше.
Новая приходит со статусом `draft` и пустыми `sanctions` — пределы
наказания вносит юрист, из текста они не выводятся.

После любой правки — `second-opinion norms-seal`.

## Что сделать по каждой норме

1. Поднять историю изменений статьи по официальному источнику
   (КонсультантПлюс / pravo.gov.ru) за период с даты в колонке
   «Заявлено с» по настоящее время.
2. Если статья **действительно не менялась** — зафиксировать это: в `note`
   файла указать дату сверки истории и источник. Тогда единственная
   редакция становится подтверждённым фактом, а не допущением.
3. Если менялась — внести недостающие редакции по правилам
   [DATA_SOURCES.md](DATA_SOURCES.md): точные границы `effective_from` /
   `effective_to`, `source_url`, `retrieved_at`, обновлённые `sanctions`.
4. Прогнать `make test` и `second-opinion norms-coverage`.

Тексты редакций вносит юрист по официальному источнику. Заполнение «по
памяти» запрещено [DATA_SOURCES.md](DATA_SOURCES.md) и в судебной системе
недопустимо.

## Еженедельная проверка

Закон меняется без нашего участия, и узнать об этом система должна не на
демонстрации. Workflow `.github/workflows/norms-watch.yml` по понедельникам
проверяет целостность корпуса, собирает наряд на сверку и сверяет
действующие редакции с ИПС. Если источник знает более новую редакцию —
заводится issue с меткой `norms-watch` (при повторах дописывается
комментарий, а не плодятся новые issue).

Автоматика **обнаруживает и зовёт юриста, но не обновляет норму**: ни один
шаг не трогает `data/fixtures/norms`. Молча подставить свежую редакцию
запрещено правилом «never» из
[LEGAL_SAFETY_PRINCIPLES.md](LEGAL_SAFETY_PRINCIPLES.md), и на этот
workflow оно распространяется тоже.

Недоступность ИПС и устаревание нормы различаются по коду возврата
(2 и 1): упавший чужой сервер не превращается в issue о том, что закон
изменился.

После 08.09.2026 корпус вырос до 31 нормы (добавлена глава 11 и другие), на
06.10.2026 сверки требуют 18 из 31. Актуальный список даёт
`second-opinion norms-coverage`, таблицы ниже остаются снимком на дату.

## Сравнение крайних редакций УК РФ (06.10.2026)

Черновик для юриста, получен командой `norms-check-amendments` по ИПС
(документ 102041891, исходная редакция и редакция 365 от 04.08.2026 № 300-ФЗ):

| Статья | Результат |
|---|---|
| 60, 66 | не менялась: текст совпадает с исходной редакцией |
| 61, 64, 73, 75, 76 | менялась: текст отличается от исходной редакции |
| 112, 161, 163, 228 | менялась: текст отличается от исходной редакции |
| 76.2 | не сверена: в исходной редакции статьи нет (введена позже) |

Для шести норм с пределами санкции (ст. 112 ч. 1, 161 ч. 1 и 2, 163 ч. 1,
228 ч. 1 и 2) это означает, что запись «одна редакция с 1996 года» неверна:
статьи менялись, и на даты до изменения система применила бы текущий текст.
Команда сравнивает только крайние редакции и не говорит, что именно
изменилось и затронуло ли изменение санкцию; 153 редакции из 366 у источника
не подготовлены. Список изменений по каждой статье и подтверждение
(`norms-confirm-history`) остаются за юристом. До этого отчёт по делу
называет такие нормы в замечании «Редакционная история норм не сверена».

## Что видит судья в отчёте по делу

Отчёт о покрытии читает оператор, а судья видит только результат анализа.
Поэтому две оговорки переносятся в раздел «проблемные места» самого отчёта
(`legal_sources.coverage.history_caveats`, показывает `reporting`):

- **«Редакционная история норм не сверена»** - у применённой нормы одна
  редакция старше десяти лет и юрист не подтвердил отсутствие изменений.
  Текст называет норму, дату начала редакции и дату дела.
- **«Дата применения близка к границе редакции»** - дата дела не позже 90
  дней после начала не первой редакции. Граница из ИПС - дата акта, а
  вступление в силу может быть позже; окно в 90 дней - эвристика.

Оговорки не меняют статусов проверок и не выбирают другую редакцию. Пометка
о неподтверждённой истории исчезает после `norms-confirm-history`.

## Чего отчёт не проверяет

- **корректность самих текстов** — только полноту редакционных интервалов;
- **актуальность действующей редакции**: нормы сверены по КП 03.09.2026,
  более поздние поправки отчёт не увидит;
- **целостность файла фикстуры** — это отдельная проверка,
  `second-opinion norms-seal --check` (см. [DATA_SOURCES.md](DATA_SOURCES.md)).
