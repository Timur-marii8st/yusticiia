# ADR-006: Хранилище MVP — файловые репозитории за интерфейсами

- Статус: принят (2026-08-25); обновлён (2026-08-26): PostgreSQL-бэкенд реализован как опция

## Контекст

Задание рекомендует PostgreSQL + SQLAlchemy. Однако первому вертикальному
срезу нужна «одна команда для запуска» без поднятия СУБД, а инфраструктурная
сложность на старте прямо запрещена принципом «не переусложняй».

## Решение

Доменные данные живут за интерфейсами репозиториев
(`DocumentRepository`, `NormStore`, `CaseRepository`, `AnalysisRepository`).
MVP-реализация — JSON-файлы в каталоге данных (атомарная запись,
идентификаторы — UUID). Реализации выбираются конфигурацией.

Переход на PostgreSQL выполняется заменой реализации репозиториев
— доменные модели и бизнес-логика не изменяются. С 2026-08-26 доступен
`PostgresJsonRepository` (JSONB, таблицы `documents`/`analyses`, интерфейс
идентичен файловому). Выбор бэкенда — переменной окружения
`SO_STORAGE_BACKEND=file|postgres` + `SO_DATABASE_URL` (см.
`docker-compose.yml` профиль `postgres`).

## Альтернативы

- **Сразу PostgreSQL + pgvector:** рабочий, но до первого поискового
  контура это инфраструктура ради инфраструктуры; усложняет тесты и демо.
  Отложено до M5.
- **SQLite без SQLAlchemy:** мало преимуществ перед JSON при нашем объёме
  данных; отклонено.

## Последствия

+ запуск без внешних сервисов, тривиальные резервные копии каталога;
+ миграция доказана интеграционными тестами против реального PostgreSQL
  (`SO_TEST_DATABASE_URL`, профиль `postgres` в compose);
− нет одновременного доступа нескольких процессов на файловом бэкенде
  (принимаем для MVP), транзакционность ограничена одним документом записи;
  postgres-бэкенд снимает это ограничение, но аудит-журнал остаётся файловым.
