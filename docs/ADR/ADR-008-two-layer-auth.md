# ADR-008: Двухслойная авторизация — сосуществование SO_AUTH_TOKEN и JWT

- Статус: принят (2026-09-03, итерация 0.21)
- Связано: ROADMAP п. 6, SECURITY.md п. 6, API.md, итерация 0.20 (user store)

## Контекст

В проекте исторически два независимых слоя:

1. **Loopback-MVP** (`SO_AUTH_TOKEN`, общий Bearer-секрет): HTTP-middleware
   в `create_app` требовал `Authorization: Bearer <токен>` на всех `/api/*`.
2. **JWT** (0.17, персональные учёные записи): `/auth/login` → access/refresh,
   `get_current_user` проверяет access-токен, `require_role(admin)` — CRUD.

Дефект до ADR-008: при заданном `SO_AUTH_TOKEN` middleware сравнивал
заголовок строго с общим секретом и **отвергал валидные JWT access-токены**
на `/api/*`. Слои были взаимоисключающими: либо общий секрет (без
персонализации), либо JWT (только при выключенном `SO_AUTH_TOKEN`).
Аутентификационный роутер при этом живёт на префиксе `/auth/*` (вне `/api/*`),
поэтому `login/refresh` всегда открыты, а `users/audit` защищены JWT —
это сохраняется.

## Решение

**Унификация через «или» (без ломки совместимости):**

- если `SO_AUTH_TOKEN` не задан — поведение прежнее (открытый loopback-MVP);
- если задан — `/api/*` принимает **любой** из двух credentials:
  `Bearer <SO_AUTH_TOKEN>` **или** валидный JWT access-токен
  (проверка через `AuthService.decode_token`: подпись, срок, `type=access`,
  пользователь существует и активен);
- `/auth/login`, `/auth/refresh` остаются открытыми (иначе вход невозможен);
- `/auth/me`, `/auth/users/*`, `/auth/audit`, `/auth/change-password`,
  `/auth/logout` требуют JWT (как раньше, через зависимости);
- `/health`, `/metrics`, `/`, `/static/*` открыты всегда.

Миграционный путь: оператор может включить `SO_AUTH_TOKEN` для грубого
периметра и постепенно переводить клиентов на JWT — оба работают
параллельно. Отключение `SO_AUTH_TOKEN` оставляет только JWT.

## Альтернативы

- **Разделить слои строго (секрет ИЛИ JWT, но не оба):** отклонено —
  ломает существующих клиентов loopback-MVP при включении JWT.
- **Перенести auth-роутер под `/api/*`:** отклонено в этой итерации —
  ломает пути `/auth/*`, зафиксированные тестами и UI; возможно позже
  с версионированием.
- **Убрать `SO_AUTH_TOKEN` совсем:** рано — нужен для простых
  однотокенных развёртываний за прокси и для обратной совместимости.

## Последствия

+ JWT работает на `/api/*` и при включённом периметре;
+ старые клиенты с общим секретом не ломаются;
+ правило зафиксировано тестами (`test_api_jwt_accepted_when_token_set`,
  `test_api_rejects_garbage_when_token_set`);
− middleware тянет `AuthService` (глобальный синглтон) — приемлемо для MVP;
  при Postgres-бэкенде проверка JWT делает lookup пользователя в БД.
