## 1. Токен ГАРАНТ недоступен

**Суть.** `GET /v2/redactions/$topic` — единственный найденный источник,
который прямо отдаёт редакционную историю статьи. Доступ только по
OAuth-токену, который выдаёт обслуживающая организация по заявке.
Токена нет и сроки неизвестны.

**Что установлено.** Документация API прочитана. Ответ `redactions`
содержит `activity[]` (периоды `from`/`to`), `changingDocuments[]`
(чем внесено изменение), `status` (`rs_Actual`, `rs_Old`, …) и
`notSure[]` — периоды неопределённости. Это ложится на существующую
`NormVersion` почти дословно, а `notSure[]` совпадает с принципом
«не скрывать неопределённость» из `ENGINEERING_RULES`.

Лимиты: 30 запросов/мин на документ, 300 документов в `find-modified`,
20 с на запрос, коды `423` и `429` при превышении.

### Варианты

**А. Провайдер + заглушка по контракту** *(рекомендую)*

Развязка ровно та же, что уже применена к LLM (`llm/provider.py`:
`Protocol` + мок по умолчанию + реальный провайдер по конфигурации):

```
LegalSourceProvider (Protocol)
├── GarantProvider        — HTTP-клиент, пишется сейчас, вживую не проверен
└── StubGarantProvider    — отвечает из фикстур, для разработки и тестов
```

Плюс команда сверки контракта: при появлении токена она дёргает
`/v2/limits` и один известный документ и сравнивает фактическую форму
ответа с той, что заложена в фикстуры. Расхождения видны сразу, а не
через неделю отладки.

*Честная оговорка, которую нельзя замалчивать:* фикстуры будут
**предположением по документации, а не записанным ответом сервера**.
Называть их «записанными» нельзя — по тем же правилам, по которым
синтетические дела в проекте помечены `synthetic: true`. В файлах
фикстур это должно стоять явным полем, иначе однажды кто-то примет их
за реальные данные.

Риск: любое имя поля может не совпасть. Поэтому слой преобразования
`ответ ГАРАНТ → NormVersion` держим тонким и в одном месте.

**Б. Ждать токен, ничего не писать**

Ноль риска впустую написанного кода, но и ноль движения. Если токен
придёт за неделю до сдачи, интеграции не будет.

**В. Ручной экспорт из веб-версии ГАРАНТ**

Юрист открывает статью, копирует историю редакций, складываем в
фикстуры обычным порядком (`draft` → сверка → `norms-seal`). Не требует
API вообще и даёт настоящие данные, а не предположения. Медленно, но по
12 нормам приоритета 1 — реально.

**Г. Отказаться от ГАРАНТ**

Тогда редакционная история собирается вручную по КонсультантПлюс, как
уже делалось при сверке 03.09.2026. Для 20–30 статей это рабочий путь.

### Рекомендация (пересмотрена 14.09.2026)

**Ждать без спешки.** После закрытия вопроса 3 редакционная история
берётся из ИПС `pravo.gov.ru` — государственного источника без токена.
ГАРАНТ из критического пути стал улучшением: он отдаёт периоды действия
редакций вместо дат актов, то есть снимает ровно ту оговорку, с которой
сейчас работает юрист.

Написанный клиент (`garant.py`) и заглушка остаются: в день получения
токена меняется переменная окружения. Заявку подавать стоит, но проект
на неё больше не завязан, и лицензионный вопрос (п. 2) перестал быть
блокирующим.

## 2. Правовые условия использования ГАРАНТ в конкурсной работе

**Суть.** ГАРАНТ — коммерческая система. Прежде чем строить на ней
подсистему, нужно понимать: допускает ли лицензия использование API в
конкурсной работе, можно ли хранить полученные тексты в своей базе,
и что происходит с системой, когда подписка кончается.

**Что установлено.** Ничего. Документация описывает технику, не условия.

**Варианты:** запросить условия вместе с заявкой на токен · заложить
архитектуру так, чтобы ГАРАНТ был одним из провайдеров, а не
единственным · выяснить, есть ли у суда уже действующая подписка.

**Рекомендация.** Задать вопрос об условиях **в той же заявке**, что и
токен. Это один разговор, а ответ влияет на то, имеет ли смысл вариант А
вообще.

## 3. Отдаёт ли ИПС pravo.gov.ru консолидированные редакции — ЗАКРЫТ

**Ответ: да.** Проверено 14.09.2026, документ 102041891 (УК РФ).

**Что установлено фактами.** Сайт открывается — прежняя недоступность
была ограничением окружения и ушла. На странице документа лежит список
из 366 редакций: исходная и 365 изменяющих актов, у каждой указаны номер
закона и его дата. Редакция адресуется параметром `rdk`, полный текст
приходит по `?doc_itself=&nd=…&page=1&rdk=N&fulltext=1`. Тексты статей
настоящие и консолидированные.

**Следствия.**

1. **Свой движок применения поправок не нужен** — источник отдаёт готовые
   редакции. Это и был вопрос-гейт из ТЗ.
2. **Токен ГАРАНТ перестал быть критическим путём** (см. вопрос 1).
3. Реализовано: `legal_sources/pravo_gov.py`, `SO_REDACTION_SOURCE=pravo`,
   команда `norms-check-amendments`.

**Что источник не даёт.** Дату вступления редакции в силу (в списке —
дата акта); 153 редакции из 366 помечены «не готова» и недоступны.
Обе оговорки отражены в выдаче и в [DATA_SOURCES.md](DATA_SOURCES.md).

## 4. Редакции по 15 нормам

**Суть.** Аудит показал: 15 норм из 27 заявляют «не менялась» с даты
принятия кодекса, из них 6 несут пределы санкции, которые читает движок
правил. Наряд — `docs/NORM_COVERAGE.md`.

**Что установлено.** Разрывов в покрытии нет; все 15 попали по признаку
незафиксированной истории. Тексты я вносить не могу — нужен официальный
источник и юридическая сверка.

**Варианты:** юрист проходит наряд по КонсультантПлюс · ждать ГАРАНТ и
получить историю программно · подтвердить «не менялась» там, где это
правда, и закрыть часть норм без внесения редакций.

**Рекомендация.** Начать с третьего: по части статей утверждение может
оказаться верным, и тогда достаточно зафиксировать факт сверки в `note`.
Это дёшево и сокращает список.

## 5. Russian-Law-MCP — ЗАКРЫТ

**Суть.** Предлагался как быстрый baseline.

**Что установлено (проверено 17.09.2026).** Репозиторий существует:
`shodenis/Russian-Law-MCP` (Ansvar Systems, Стокгольм), TypeScript,
12 369 федеральных законов, 77 647 положений, FTS5, Apache 2.0, удалённый
MCP-endpoint. Прежняя запись в этом файле — «репозиторий отдаёт 404,
вероятный настоящий `Ansvar-Systems/russian-law-mcp` не подтверждён» —
**была ошибкой**: искали не того владельца.

Вывод от этого не изменился, но теперь он опирается на их собственный
`COVERAGE_LIMITATIONS.md`, а не на догадку:

- *«Historical Statute Versions — Limited: Only current text is available.
  No systematic tracking of amendments over time»*;
- *«Court Decisions — Not Included»* — включая постановления Пленума ВС;
- региональное законодательство не включено.

База собрана импортом из RusLawOD и наследует его ограничение: исходные
редакции, а не консолидированные.

**Решение.** Не используется: не закрывает ни редакции на дату, ни
Пленум — два из трёх столпов проверки. Ради полнотекстового поиска по ФЗ
своя база из 27 выверенных норм полезнее 12 тысяч непроверенных.
Вернуться — если появится история редакций.

## 7. Чем читать статьи, скачанные из интернета

**Суть.** Официальная публикация выкладывает акты в PDF, часто сканами.
Вопрос — как получать из них текст.

**Что установлено.**

*Для норм извлечение текста — не узкое место.* В `NormVersion.text`
лежит не текст закона, а выверенное изложение:

```
text:      «Ч. 1 ст. 158 УК РФ в редакции 1996–2003 (сверено 03.09.2026):
            лишение свободы на срок до трех лет (36 мес.).»
sanctions: [{punishment_type: imprisonment, max_months: 36}]
```

`max_months: 36` не извлекается из PDF никаким распознаванием — это
вывод юриста из текста санкции. Идеальный OCR даёт текст статьи и ни
одной структурной санкции. Узкое место — юридическая сверка и
структурирование, а не чтение файла.

*Формат зависит от источника.* ГАРАНТ отдаёт **HTML**
(`/v2/topic/$topic/html` и `/v2/topic/$topic/entry/$entry/html`), а не
PDF. По главному пути проблема не возникает вовсе. PDF остаётся только
у `publication.pravo.gov.ru`.

*В проекте уже есть чтение PDF.* `ingestion/parser.py`: текстовый слой
через `pypdf`, при пустом слое — OCR-фолбэк (`pytesseract` + `pdf2image`,
группа зависимостей `ocr`), при недоступном OCR — честная ошибка вместо
пустого документа. Но подключено это только к загрузке судебных
документов пользователем; `scripts/fetch_pravo.py` требует готовый
`--text-file`, то есть текст нормы сегодня готовится вручную.

Локально `tesseract` не установлен, группа `ocr` не поставлена; в
`Dockerfile` `tesseract-ocr-rus` уже прописан.

### Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| **HTML-источники в приоритете**, PDF хранить как контрольный первоисточник | распознавание не нужно; текст чистый и с разметкой | зависит от доступности ГАРАНТ или ИПС |
| **Текстовый слой PDF** (`pypdf`, уже есть) | работает на большинстве официальных публикаций, без внешних зависимостей | переносы, колонтитулы и сноски приходят вперемешку — нужна нормализация |
| **OCR локально** (`tesseract` + `rus`, уже есть как фолбэк) | закрывает сканы; данные не покидают контур | ошибка в цифре меняет смысл нормы; требует установки |
| **Внешний OCR-сервис** (Yandex Vision, ABBYY) | качество выше | документ уходит во внешний контур; для публичных норм допустимо, для судебных актов — нет |

**Отдельная опасность.** В праве ошибка распознавания в числе меняет
смысл: «до трёх лет» против «до трети», «36» против «86». Поэтому любой
машинно извлечённый текст обязан оставаться `draft` до юридической
сверки. В проекте это уже так: фикстура не выходит из `draft` без сверки
и опечатывания.

### Рекомендация

Первый вариант основным, второй — когда есть только PDF, третий —
фолбэком для сканов. Внешние сервисы пока не нужны: объём норм
измеряется десятками статей, а не тысячами.

Конкретный шаг, который можно сделать сразу и без новых зависимостей:
подключить существующий `parse_pdf` к `scripts/fetch_pravo.py`, чтобы
`--text-file` стал необязательным. Скрипт скачивает PDF, вытаскивает
текст и кладёт черновик, который юрист правит, а не набирает заново.
