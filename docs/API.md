# API

Базовый адрес: `http://127.0.0.1:8000` (loopback). Ответы — JSON, кроме выгрузки заключения в .docx.

**Авторизация.** Два слоя, работают совместно:
- `SO_AUTH_TOKEN` — общий Bearer-секрет для loopback-MVP. Если задан,
  `/api/*` принимает `Authorization: Bearer <токен>` **или** валидный JWT
  access-токен; без того и другого — `401`.
  `/health`, `/metrics`, `/` и `/static/*` открыты всегда.
- JWT (`POST /auth/login`) — персональные учётные записи. После `login`
  все защищённые эндпоинты принимают `Authorization: Bearer <access_token>`.
  Роли: `judge` (по умолчанию), `clerk`, `admin`. Роль `admin` обязательна
  для чтения `/auth/users` и `/auth/audit`. Ключ подписи — `SO_JWT_SECRET`, **отдельный** от
  `SO_AUTH_TOKEN`: общий Bearer раздаётся операторам, и знание его не
  должно позволять подписать токен с ролью `admin`.

**Почему auth-эндпоинты вне `/api/`.** Роутер смонтирован по `/auth/*`, то
есть middleware общего Bearer его не покрывает. Иначе вход был бы
невозможен: чтобы получить токен, пришлось бы уже иметь токен. Защита
`/auth/*` строится на самом JWT и проверке роли (`require_role`), что
строже общего секрета: `SO_AUTH_TOKEN` один на всех операторов, а
`/auth/users` и `/auth/audit` требуют персональной учётки с ролью `admin`.
Учётные записи и пароли через HTTP не создаются и не меняются: это команды сервера
`second-opinion create-admin`, `create-user`, `update-user`, `delete-user`, `reset-password`,
`list-users` (работают и с файлами, и с PostgreSQL).

Интерактивная спецификация: `/docs` (Swagger UI, генерируется FastAPI).
Формы ответов описаны моделями (`api/schemas.py`), поэтому `/openapi.json`
пригоден для генерации клиента: на 07.10.2026 это 34 операции и 75
именованных моделей, включая полное дерево `AnalysisReport` — факт,
доказательство, правило, ссылка на редакцию нормы. Хэш и история паролей
в схему не попадают ни при каком ответе (проверяется тестом).

`/docs` и `/openapi.json` открыты без авторизации — тем же путём, что
`/health` (см. выше). Поэтому поле `description` из схемы вычищено: без
этого FastAPI копирует туда docstring обработчика целиком, а докстринги
рассчитаны на читателя кода, не на анонимного посетителя интерфейса.
Форма ответа (пути, параметры, модели, `summary`) не страдает —
удаляется только свободный текст (проверяется тестом).

`GET /api/v1/norms/{norm_id}` всегда содержит оба ключа — `versions` и `version`;
неприменимый равен `null`.

## Документы

| Метод и путь | Назначение | Коды |
|---|---|---|
| `POST /api/v1/documents` | создать документ из текста `{filename, text}` | 200; 400 — превышен лимит размера; 413 — тело запроса больше допустимого (`SO_MAX_UPLOAD_BYTES` × 4); 422 — пустой текст или нет обязательного поля |
| `POST /api/v1/documents/upload` | загрузить файл (multipart, поле `file`); TXT/MD/DOCX/PDF с текстовым слоем, опционально OCR для сканов. Чтение обрывается на `SO_MAX_UPLOAD_BYTES`, запрос сверх лимита в память не буферизуется | 200; 400 — пустой файл, неподдерживаемый формат, превышен лимит; 413 — тело запроса больше допустимого |
| `GET /api/v1/documents/{id}` | текст документа + SHA-256 | 200; 404 |
| `DELETE /api/v1/documents/{id}` | удалить документ **и все отчёты по нему** (каскад) | 200; 404 |

## Версия API

Канонический префикс — `/api/v1`. Прежние пути без версии (`/api/...`)
продолжают обслуживаться как псевдонимы: их зовут интерфейс, скрипты и
тесты, и одномоментная замена ради чистоты обошлась бы дороже, чем стоит.
В спецификации OpenAPI описан только канонический путь — два одинаковых
описания вводили бы в заблуждение.

Версия появилась заранее: у будущих несовместимых изменений должно быть
куда переезжать, иначе их либо не делают, либо ломают работающих
клиентов.

## Формат ошибок

Любая ошибка приходит в одной форме:

```json
{
  "detail": "норма не найдена: uk-rf:art-1",
  "error": {
    "code": "not_found",
    "message": "норма не найдена: uk-rf:art-1",
    "request_id": "9f2c…",
    "fields": [{"location": "body.text", "message": "Field required"}]
  }
}
```

`code`: `bad_request`, `unauthorized`, `forbidden`, `not_found`,
`conflict`, `payload_too_large`, `validation_error`, `too_many_requests`,
`internal_error`, `service_unavailable`.
`fields` появляется только у ошибок валидации. `detail` сохранён для
совместимости и всегда строка — прежде при 422 там лежал список
объектов, и клиенту приходилось угадывать форму по коду ответа.

## Окно выдачи в списках

`GET /api/v1/norms` и `GET /api/v1/cases` принимают `limit` и `offset` и
возвращают рядом с данными объект `page`:
`{"total", "limit", "offset", "has_more"}`. Значения по умолчанию
покрывают нынешний объём целиком, поэтому существующие клиенты ничего не
замечают; окно введено заранее, чтобы рост корпуса не стал ломающим
изменением.

## Сквозной идентификатор запроса

Каждый ответ несёт заголовок `X-Request-Id`. Если клиент прислал свой
(печатаемый ASCII, до 64 символов) — он сохраняется, иначе выдаётся новый.
Тот же идентификатор попадает в структурные логи и в аудит-журнал, то
есть по нему можно найти запись о конкретном действии. Ответ 401 его тоже
несёт: ошибка — как раз тот случай, когда идентификатор нужен.

## Анализ

| Метод и путь | Назначение | Коды |
|---|---|---|
| `POST /api/v1/documents/{id}/analyze` | полный конвейер: факты -> проверки -> практика -> аналитика. Тело (необязательно): `{"applicable_at": "ГГГГ-ММ-ДД"}` — юридически значимая дата для выбора редакции норм; дата не в формате ГГГГ-ММ-ДД даёт 422, пустая строка равна отсутствию | 200; 404; 422; 429 — слишком частые запуски (`SO_ANALYZE_RATE_LIMIT`); 503 — все места для анализа заняты (`SO_ANALYZE_MAX_CONCURRENCY`) |
| `GET /api/v1/analyses` | история дел: сводки анализов актора, новые сверху. Параметры: `limit` (по умолчанию 50), `scope=own\|all`. `scope=all` доступен только администратору и возвращает 403 остальным. В сводке имя файла, квалификация, число обстоятельств и счётчики статусов проверок — без содержимого отчёта | 200; 403 |
| `GET /api/v1/analyses/{id}` | отчёт анализа целиком | 200; 404 |
| `GET /api/v1/analyses/{id}/document` | заключение в .docx, альбомная страница с таблицами (параметр `mask=true` скрывает персональные данные в файле): дело и документ с данными личного кабинета, изложение с обстоятельствами в основе, проблемные места, проверки с нормами, редакциями и расчётом, обстоятельства с цитатами, практика, вся описательная статистика, применённые нормы. Содержит только то, что есть в отчёте | 200; 404 |
| `GET /api/v1/analyses/{id}/print` | печатная форма заключения: те же разделы и таблицы, что в .docx, страницей HTML (параметр `mask=true` скрывает персональные данные); интерфейс открывает её в скрытой рамке и вызывает печать браузера | 200; 404 |
| `DELETE /api/v1/analyses/{id}` | удалить отчёт | 200; 404 |

## Человек в контуре

| Метод и путь | Назначение | Коды |
|---|---|---|
| `PATCH /api/v1/analyses/{aid}/facts/{fid}` | подтвердить факт (`{"status":"VERIFIED"}`), исключить (`{"status":"NOT_FOUND", "reason": "…"}`) или исправить значение (`{"value": …}`); отчёт пересчитывается детерминированно | 200; 400 (недопустимый статус/значение, VERIFIED без цитаты, NOT_FOUND без `reason`); 404 |
| `POST /api/v1/analyses/{aid}/facts` | добавить обстоятельство «с нуля»: `{"type", "value", "quote"}`. Цитата обязана дословно находиться в документе | 200; 400 (цитата не найдена, неизвестный тип, значение не по схеме); 404 |

Исключение факта (`NOT_FOUND`) требует непустой `reason` — мера по риску
№ 5 Приложения № 3 к Концепции ВС РФ по ИИ («обязательная мотивировка
отклонения ИИ-рекомендации»). Причина сохраняется на факте
(`rejection_reason` в ответе), пишется в аудит-журнал (`fact_update`,
поле `reason`) и попадает в .docx-заключение. Повторное подтверждение
факта (`VERIFIED`) или правка значения очищают причину — она относится
только к текущему исключению.

## Нормы и источники

| Метод и путь | Назначение | Коды |
|---|---|---|
| `GET /api/v1/norms` | список норм базы | 200 |
| `GET /api/v1/norms/coverage` | состояние корпуса: покрытие редакциями, что требует юридической сверки, цел ли манифест | 200 |
| `GET /api/v1/norms/{norm_id}?applicable_at=…` | норма со всеми редакциями либо конкретной редакцией на дату | 200; 400 (неверная дата); 404 |
| `POST /api/v1/norms/{norm_id}/confirm-history` | зафиксировать сверку истории: статья действительно не менялась (`checked_through`, `source`) | 200; 400 (норма не найдена/нет источника); 403 (не администратор); 409 (носитель не файловый) |
| `POST /api/v1/norms/{norm_id}/add-version` | добавить редакцию (`text`, `effective_from`, опционально `effective_to`/`version_id`/`source_url`/`source_edition`); закрывает предыдущий интервал, приходит статусом `draft` | 200; 400; 403; 409 |
| `GET /api/v1/search?q=…&limit=&code=&article=&article_suffix=&part=&applicable_at=` | лексический/гибридный поиск; явная статья УК РФ на дату дополнительно возвращает `source_state` с локальным снимком и внешним кандидатом | 200; 400 (нет даты для явного УК/неверная дата); 422 (нет запроса/недопустимые реквизиты) |

Наряд на сверку в `coverage` считается той же функцией, что и
`second-opinion norms-coverage`, — числа в CLI и в API совпадают по
построению. Свежесть относительно внешнего источника там не
проверяется. Для операторской сверки есть `norms-check-updates`; для
явного запроса статьи и получения источников анализа — отдельная настройка
`SO_DYNAMIC_NORM_SOURCE=pravo` с ограниченным таймаутом и кэшем.

При явном запросе УК РФ `q` необязателен; `article`, `code=УК РФ` и
`applicable_at` обязательны. Кандидат с неизвестными юридическими датами
возвращается в `source_state.candidate` со статусом `candidate`, без
выдуманного `effective_from`. `source_state` различает получение, применимость,
актуальность и проверку санкций, включая виды наказания, требующие сверки.
Ошибки провайдера остаются состояниями в ответе 200 с причинами; они не
считаются пустым результатом поиска. Пример полного происхождения —
[LEGAL_RAG](LEGAL_RAG.md#api), политика обновления — [DATA_SOURCES](DATA_SOURCES.md#кэш-ошибки-и-воспроизводимость).

Обе правки корпуса доступны только роли `admin` и только при файловом
носителе норм (`SO_NORMS_BACKEND=file`, по умолчанию). Точку отсчёта для
`norms-check-updates` (`--source-document`) `confirm-history` не
проставляет — она требует запроса к ИПС, а медленному внешнему серверу не
место в обработке HTTP-запроса, как и в `coverage` выше; ставится отдельно
из терминала. После каждой правки корпус переопечатывается автоматически
и живой `NormStore` обновляется на месте — без перезапуска процесса.
Обе операции пишут в аудит-журнал (`norm_confirm_history`/
`norm_add_version`, с `actor`, id нормы и деталями правки) — как через
API, так и через одноимённые команды CLI (`actor: "cli"` там, где личная
учётная запись не опознаётся).

## Аутентификация и управление пользователями

| Метод и путь | Назначение | Коды |
|---|---|---|
| `POST /auth/login` | вход: `{"email", "password"}` -> `{"user", "tokens": {access_token, refresh_token, expires_in}}`; с `"cookie": true` refresh не отдаётся в теле (`null`), а ставится в cookie `so_refresh` (`HttpOnly`, `SameSite=Strict`, `Path=/auth`, без срока: до закрытия браузера; `Secure` по HTTPS или при `SO_COOKIE_SECURE=1`) | 200; 401 — неверный email или пароль, а также вход заблокирован после неудачных попыток (`SO_LOGIN_MAX_ATTEMPTS`): ответы одинаковы, чтобы не выдавать существование аккаунта; 403 — срок пароля истёк (`SO_PASSWORD_MAX_AGE_DAYS`); 429 — превышен лимит попыток с клиента (`SO_LOGIN_RATE_LIMIT`), в ответе `Retry-After` |
| `POST /auth/refresh` | обновить access-токен **с ротацией**: `{"refresh_token"}` -> новая пара; старый refresh отзывается, повтор — 401. Без тела токен берётся из cookie `so_refresh`, и тогда нужен заголовок `X-SO-CSRF` (любое значение), новый refresh возвращается в cookie, а не в теле | 200; 401; 403 — cookie без заголовка `X-SO-CSRF` |
| `GET /auth/me` | текущий пользователь (по access-токену) | 200; 401 |
| `POST /auth/logout` | выход; тело опционально `{"refresh_token"}` — отозвать refresh (blacklist); refresh из cookie `so_refresh` отзывается тоже, cookie удаляется. Без тела и cookie — как раньше | 200; 401 |
| `GET /auth/audit?limit=` | аудит входов (только admin, новые первыми, без паролей) | 200; 401; 403 |
| `GET /auth/users` | список пользователей (только admin, только чтение) | 200; 401; 403 |

Хранилище пользователей — `AuthService` за интерфейсом `UserStore`
(`src/second_opinion/auth/repository.py`): in-memory по умолчанию
(loopback-MVP, один процесс); при `SO_STORAGE_BACKEND=postgres` +
`SO_DATABASE_URL` — PostgreSQL (таблицы `users` JSONB,
`auth_refresh_blacklist`, `auth_login_audit`).
Refresh-токены — с ротацией (`jti` в `TokenPayload`): предъявленный refresh
отзывается до выпуска новой пары. Истечение паролей —
`SO_PASSWORD_MAX_AGE_DAYS=0` (выкл. по умолчанию). Аудит входов —
`GET /auth/audit` (admin).

## Инварианты (действуют на всех эндпоинтах)

1. Ни один юридически значимый результат не существует без provenance:
   факт -> цитата с оффсетами -> правило/норма -> редакция -> источник.
   Аудит-журнал дополнительно фиксирует исполнителя (`actor`): `user_id`
   учётной записи, `shared-token` при входе по общему секрету либо
   `anonymous` в открытом loopback-режиме.
2. Поиск возвращает только реально хранящиеся фрагменты; пустой результат
   честнее выдуманного ответа.
3. Текст документа — недоверенные данные (prompt injection не меняет
   поведение системы).
4. Статистика по делам — только описательная.
5. Любой auth-эндпоинт `users` (CRUD) требует роль `admin`.
